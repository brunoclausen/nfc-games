- dmesg viser at `pn533_usb`'s probe fejler men outputtet _ikke_ forårsager timeout:
  `pn533_usb 3-2:1.0: probe with driver pn533_usb failed with error -5`.
- Fuldt power-cycle (xvdc authorized toggling via sysfs) udbedrede **ikke** fejlen.

### 2.2 Trinvis USB-probe (libusb direkte)

Et minimalt C-program (libusb bulk-transfer direkte) afslørede mønstret.
Probe kørte `open → claim → IccPowerOn → FF 00 51 → SAMConfiguration → RF on → GetFirmware`:

```
IccPowerOn:
  write[10]: OK (tr=10)
  read: rc=0 OK (tr=10) bytes: 83 00 00 00 00 00 00 02 FE 00
FF 00 51 (buzzer get?):
  write[15]: OK (tr=15)
  read: rc=0 OK (tr=12) bytes: 80 02 00 00 00 00 00 00 81 00 3B 00
SAM config:
  write[20]: OK (tr=20)
  read: rc=-7 TIMEOUT (tr=0) bytes:          <-- ACR122U hænger her
RF field on:
  write[19]: TIMEOUT (tr=0)
  read: rc=-7 TIMEOUT (tr=0) bytes:
Get firmware:
  write[15]: TIMEOUT (tr=0)
  read: rc=0 OK (tr=12) bytes: 80 02 00 00 00 00 00 02 81 00 90 FF
```

Samme sekvens **uden** `SAMConfiguration` virkede fuldt:

```
IccPowerOn: OK | FF 00 51: OK | RF field on: OK | Get firmware: OK (D5 33 90 00)
```

### 2.3 Rodårsag

`PN532 SAMConfiguration`-kommandoen (`D4 14`), sendt i `Acr122::open()` og
`Acr122::recover()`, får ACR122U-firmwaren til at fryse så alle efterfølgende
CCID bulk-writes timeout-er. Der kan kun komme til live igen ved gen-åbning
(ny proces) — og heller ikke altid dét. Selve kommandoen er unødvendig for en
kontaktløs PICC-læsning (RF-feltet er allerede aktivt).

Bemærk: `libusb_reset_device` + `libusb_detach_kernel_driver` (tidligere ucommittede
band-aids) løste ikke problemet. En tilsvarende `libusb_clear_halt` førte endda til
timeout på selve skrivningen — dvs. resets er uforudsigelige og derfor fjernet.

## 9. SENERE FUND: 24-timers-ustabilitet — root cause

Brugeren oplevede at læseren kunne blive ustabil efter ~24 timer.

### 9.1 Rodårsag fundet

Under stresstest døde USB3-controlleren (xHCI) midt i en kørsel:

```
xhci_hcd 0000:09:00.3: xHCI host not responding to stop endpoint command
xhci_hcd 0000:09:00.3: xHCI host controller not responding, assume dead
xhci_hcd 0000:09:00.3: HC died; cleaning up
usb 3-2: USB disconnect, device number 3
```

Den tidligere fix (commit `d557ae5`) kaldte `libusb_reset_device` **ved hver
lukning af læseren** (`Acr122::close()`). Ved almindelig brug er det mange
USB-resets per dag (hver kommando, hvert tag-skift, hver refresh) — så mange
USB-resets slider/stresser xHCI-controlleren og kan få den til at dø.

### 9.2 Ændringer (stabilitetsfix, uncommitted)

`cpp/acr122.cpp`:
- `close()`: fjernet `libusb_reset_device` (ingen reset ved lukning længere)
- tilføjet `reset_hw()` — sidste-udvej USB-reset, kun ved vedvarende fejl

`cpp/acr122.hpp`: offentliggjort `reset_hw()`.

`cpp/watch.cpp`:
- indført `kRefreshEvery = 15min` (USB-genåbning hver 15. minut — også mens
  et tag holdes, så lang polling ikke hænger ACR122U-firmwaren)
- genåbningsefterlatin 300 ms efter lukning (`kReopenSettle`)
- idle-polling: 1 s i stedet for 700 ms ved > 30 s uden tag
- ved vedvarende fejl: `reset_hw()` kun efter det er gentaget (sidste udvej),
  i stedet for at hidkalde reset ved hver fejl

### 9.3 Genoprettelse efter controller-død

xHCI-genstart: `echo "0000:09:00.3" > /sys/bus/pci/drivers/xhci_hcd/{unbind,bind}`
+ fuldt power-cycle via `authorized` 0→1 (viser device igen). Appen alene kan IKKE
genoprette en død xHCI-controller — kun gen-enumering/power-cycle.
